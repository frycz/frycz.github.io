The Unified Theory of Constrains

September 19, 2026

← Back to all posts

Whenever I get a result I like out of an AI agent, I look back at what I did, and it never looks like I gave great instructions. It looks like I chose good limits.

I'd been thinking of my prompts as requests, the way you'd ask a colleague for a favor. But the requests that worked best were the ones that closed doors. Use these three tools. Follow this style. Don't touch that folder. Stop when this test passes. Each one removed options, and somehow the result got better every time I removed more.

Then it reminded me of something much older than AI.

The painter picks the paint first

Think about how people make things. A painter doesn't start with every color that exists. They squeeze out five or six onto a palette, and that small set is a big part of why the painting looks like theirs. A musician picks a handful of sounds for an album and lives inside them for a year. A sculptor chooses marble or wood, a chisel or a rasp, and those choices decide half the shape before the first cut.

None of these people feel trapped by their choices. The choices are where the style comes from. An artist with infinite options and no limits usually produces nothing, or produces mud.

Working with an AI model feels like that. The painter starts with an empty canvas and adds. With a model, you start with a canvas that already holds every possible picture at once, and your job is to take things away until only the one you want is left. That's much closer to sculpting than painting. You're cutting away stone.

From instructing to designing space

For most of computing history, we told machines exactly what to do, step by step. Load this, compare that, if this then that. The computer did nothing we didn't spell out.

Agents don't work this way, and trying to make them do so is exhausting. You can't list every step for "build me a small web app for tracking my runs." There are thousands of steps and you don't know most of them in advance. That's the whole reason you asked.

What you can do is shape the room the agent works in. Tell it to use React and Tailwind, and you've closed off Vue, Angular and hand-written CSS without mentioning them. Tell it the API should be stateless and follow REST, and you've ruled out a huge number of designs it might have wandered into. You haven't told it how to walk. You've built the hallway.

I find this a calmer way to work. I stop trying to predict every move and start asking a different question: what does the space look like where only good answers fit?

Managing the probability space

A language model works on likelihoods. Ask it something vague and it gives you the most average answer it can find, because the average is the safest bet when it knows nothing about you. That's why "write a blog post about productivity" gets you the same post everyone has already read.

Every detail you add shifts those odds. Name your audience and the average moves. Hand it an example of your writing and it moves again. Say which words you hate and a whole family of bland answers drops out. I picture it like a cloud of possible outputs that gets smaller and denser with each thing I add, until most of what's left is close to what I had in my head.

So the rule I keep coming back to is simple. The more specific the limits, the more likely the result is the one you wanted. A one-line prompt is a lottery ticket. A prompt plus a tool list plus a style guide plus a clear finish line is closer to a recipe.

This also explains something that used to confuse me. When an agent produced something strange, I'd blame the model. Now my first question is what I left open. Usually there's a door I forgot to close, and the agent walked through it, which is exactly what it should do with an open door.

The unified theory of constraints

When I say constraint, I don't mean a rule like "maximum 50 characters." I mean it much more loosely. Anything that pushes the agent down one path and away from the others counts.

The prompt itself is a constraint, maybe the biggest one, because it sets the direction before anything else happens. A list of tools for a web app is a constraint. A page of architecture guidelines for an API server is a constraint. Acceptance criteria are a constraint too, since they mark where the path ends. Even the example files you drop into the conversation count, because the agent will lean toward whatever patterns it sees in them.

Once I saw it this way, all the separate tricks people share online started to look like one idea. "Give the model a role." "Show it examples." "Write a style guide." "Use a system prompt." "Give the agent only the tools it needs." These sound like five different techniques. To me they're the same move made five ways: narrowing the space until the good answer is the likely one.

They also stack. When I build an API server with an agent, I end up with something like this:

┌──────────────────────────────────────────────────────────────┐
│  GOAL          these endpoints exist, these tests pass       │
├──────────────────────────────────────────────────────────────┤
│  PHILOSOPHY    domain-driven design, strict types,           │
│                no clever tricks                              │
├──────────────────────────────────────────────────────────────┤
│  TOOLS         Node, Express, PostgreSQL                     │
├──────────────────────────────────────────────────────────────┤
│  PROMPT        build a small production API for this         │
│                purpose                                       │
└──────────────────────────────────────────────────────────────┘

The nice thing is that each layer can change without touching the others. If I swap Node and PostgreSQL for Python and MongoDB, the prompt, the philosophy and the goal stay exactly as they were. The agent adjusts because I moved one wall of the room, and the rest of the room is still there.

Constraints you can keep

This is where the idea gets practical, and where I think most of us are wasting effort right now.

If constraints are what make the results good, then they're worth more than the results. A good set of API guidelines works for the next ten projects. A style guide I spent an evening on improves every piece of writing after it. Yet most of this work lives in a chat window and disappears when I close the tab. Next week I type a weaker version from memory.

Constraints should be treated like any other thing we build carefully. You write one down. You try it on real tasks and watch where the agent ignores it or misreads it. You fix the wording. You keep it somewhere you can find it, and you share it with people who do similar work. Someone else takes your guidelines, changes two lines for their team, and passes that version on.

Programmers already do this with code: nobody writes their own date library, they pull in one that thousands of people have tested. I'd like the same for the things that shape agents. Picture starting a project by picking a tested set of architecture guidelines, a writing voice you trust, and a short tool list, instead of starting from a blank prompt box and hoping.

The human part

This changes how I see my own role. I write less of the actual code or text than I used to. What I do more is decide what good looks like, and then describe the space where good is the only thing that fits.

That's still craft. It's the same craft the painter uses when choosing six colors out of hundreds, and it still comes from taste, experience and knowing what you want. The agent has every option in the world. Our job is to give it the right few.
